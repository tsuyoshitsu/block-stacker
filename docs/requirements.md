## 0. 30秒で分かる概要

**積み木を積む AI の成長過程を、そのままライブ配信するサービス**です。

完成した上手い AI を見せるのではなく、**下手な AI が日々少しずつ上達していく過程**を
コンテンツにします。視聴者は配信を眺めながら「昨日より積めるようになった」を楽しみます。

```
AI が積み木を掴む → 運ぶ → 置く → ときどき崩す
        ↓
  物理シミュレーションの結果を WebSocket で配信
        ↓
  視聴者のブラウザ/クライアントが 3D 描画
        ↓
  その裏で AI は学習を続け、翌営業日はもう少し上手くなっている
```

## 1. 背景とコンセプト

### 1.1 なぜ「完成品」を見せないのか

強化学習（試行錯誤を通じて行動方針を学ぶ機械学習の一分野）のデモは、たいてい
**学習済みの最良モデルを再生**します。それは「すごい」が、**一度見たら終わり**です。

本サービスが売るのは結果ではなく**過程**です。そのため以下を設計の出発点に置いています。

| 方針 | 意味 |
|---|---|
| **AI は「子供」のメタファー** | 不器用さはバグではなく演出。上手すぎる AI は作らない |
| **ゆっくり育てる** | 学習を速く回すより、視聴者が変化を追える速度を優先する |
| **アンビエント配信** | 最初から最後まで見るものではなく、隙間時間に覗く対象 |
| **連続性** | 毎回リセットせず「昨日の続き」から再開する |

### 1.2 「子供っぽさ」をどう技術で表現するか

人間の記憶構造を模した**3層記憶**を AI に持たせています。これが本プロジェクト固有の
設計で、コンセプトを技術に落とした中核部分です。

| 層 | 人間でいうと | 実装 |
|---|---|---|
| **勘** | 体に染み込んで、言葉で思い出せない感覚 | ニューラルネットの重み |
| **短期記憶** | 「ついさっき」の鮮明な記憶 | 観測データに直近5手の履歴を同梱 |
| **長期記憶** | 強烈な体験は長く残り、退屈な記憶はすぐ薄れる | 重みつき replay buffer（経験を貯める箱に、出来事の種類と到達高さで重みを付け、時間で減衰させる） |

### 1.3 想定する視聴体験

- 同時視聴者は **〜15人** 規模を想定（個人開発の演習なので大規模配信は狙わない）
- 画面には積み木と地面だけ。スコアやステージ番号などの**メタ情報は出さない**
- 「今どのくらい上手いか」は視聴者が積み上がりを見て感じ取る

## 2. 機能要件

「満たすべきこと」を機能単位で挙げます。各行の**現状**は、この資料を書いた時点で
コードに実装されているかどうかです。

### 2.1 配信（視聴者に見えるもの）

| ID | 要件 | 現状 |
|---|---|---|
| FR-01 | AI が積み木を掴み・運び・置く様子をリアルタイムに配信する | 実装済 |
| FR-02 | 視聴者はクライアントを起動するだけで接続でき、認証やアカウントは不要 | 実装済 |
| FR-03 | 接続した時点の世界の状態（全ブロックの位置・形状・色）を受け取れる | 実装済（接続時に `world_config` + `initial_state` を送信） |
| FR-04 | 以降は動いているブロックの位置が継続的に届く | 実装済（60Hz でスナップショット送信） |
| FR-05 | 積み木が崩れたことを視覚効果として扱えるよう、崩落をイベントとして通知する | 実装済（`collapse_event`。クライアント側の演出は未実装） |
| FR-06 | 通信が切れたら自動で再接続する | 実装済（クライアント側で2秒ごとに再試行） |
| FR-07 | 接続できていない間は、その旨を画面に表示する | 実装済（「サーバとの通信を試行中...」） |
| FR-08 | 4種類の形状（立方体 / 直方体 / 三角柱 / 円柱）を正しく描画する | 実装済 |
| FR-09 | ステージ番号や成功率などの内部状態は視聴者に見せない | 実装済（意図的に非公開） |

### 2.2 AI の振る舞い

| ID | 要件 | 現状 |
|---|---|---|
| FR-10 | AI は散らばった積み木から1つ選び、置き場所と向きを決めて設置する | 実装済（7次元の連続値を出力） |
| FR-11 | AI の視野は限定する（近くの積み木8個まで＋積み上がりの高さマップ） | 実装済（「子供の狭い視野」として意図的に制限） |
| FR-12 | 直近5手の履歴を判断材料に含める（短期記憶） | 実装済 |
| FR-13 | 出来事の種類（崩落・失敗・記録更新・成功・進捗なし）に応じて記憶の残りやすさを変える | 実装済（長期記憶の初期重み） |
| FR-14 | 高く積めた経験はより強く記憶に残す | 実装済（到達高さで重みを底上げ、上限3倍） |
| FR-15 | 時間が経った記憶は薄れさせる | 実装済（毎ステップ 0.9999 倍。下限 0.001） |
| FR-16 | 簡単な形状から難しい形状へ段階的に学習する | 実装済（5ステージ。立方体 → 直方体 → 三角柱 → 円柱） |
| FR-17 | 積み木を全部積み切ってしまったら、再配置してラウンドを続ける | 実装済 |
| FR-18 | 崩落を検知して、記憶上の区切りとして扱う | 実装済 |

### 2.3 学習と運用

| ID | 要件 | 現状 |
|---|---|---|
| FR-19 | **配信しながら、その裏で学習を継続できる** | 実装済（本プロジェクトの要所。§3.1 NFR-03 も参照） |
| FR-20 | 学習の成果を、配信中の AI に反映する | 実装済（50ステップごとに重みを配信側へコピー） |
| FR-21 | セッション終了時に、その日の到達点を保存する | 実装済（モデル＋長期記憶＋再開位置） |
| FR-22 | 翌営業日は保存した状態から再開し、「昨日の続き」にする | 実装済 |
| FR-23 | 前回終了からの経過日数ぶん、長期記憶を薄れさせる | 実装済（止まっている間も記憶が風化する挙動） |
| FR-24 | 配信の種になるモデル（プリセット）を定期的に生成できる | 実装済（引数なしで学習コマンドを実行＝プリセット生成） |
| FR-25 | **プリセットは意図的に「下手な」状態で止める** | 実装済（5,000ステップ。上達の壁の手前） |
| FR-26 | サーバは定時に自動で起動・停止する | 実装済（スケジューラ＋Lambda。日本の祝日はスキップ） |
| FR-27 | 強制停止されても、学習成果を失わない | 実装済（停止シグナルを受けて保存→S3へ退避） |
| FR-28 | 学習の健全性を数値で追える | 実装済（TensorBoard に報酬・成功率・到達高さ等を出力） |
| FR-29 | 配信スタックを立てずにモデルを数値評価できる | 実装済（`training.eval`） |
| FR-30 | 過去のモデルを並べて再生し、成長を比較できる | 実装済（`tools/replay_checkpoints.ps1`） |

## 3. 非機能要件

**本資料でいちばん価値があるのはここです。** 元の設計書には数値が散在していますが、
それが「守るべき目標」なのか「現状の実測値」なのかが区別されていませんでした。
分けて書き直します。

### 3.1 性能

| ID | 要件 | 根拠・区分 | 現状 |
|---|---|---|---|
| NFR-01 | 物理シミュレーションを **240Hz** で回す（1ステップ 4.17ms 以内） | **目標**。これを守れないと配信がカクつく。インスタンス選定の第一軸 | 推奨構成で達成。最低構成（2物理コア）では重い場面でコマ落ちする |
| NFR-02 | 視聴者への送出は **60Hz** | **設計決定**。240Hz の 1/4 に間引いて帯域を節約 | 実装済 |
| NFR-03 | 表示用の物理に**物理コアを1つ専有**させる | **目標**。学習スレッドと取り合うとコマ落ちする | 推奨構成（4物理コア）で確保 |
| NFR-04 | 同時視聴 **〜15人** | **目標**（想定規模） | 実測未確認。帯域計算上は数 Mbps で収まるため制約にならない見込み |
| NFR-05 | 学習速度は**速さを追わない** | **方針**。コンセプト由来。並列数を上げて賢くする必要がない | 実測 **約2.5ステップ/秒**（並列数1） |
| NFR-06 | メモリは長期記憶の容量で決まる | **制約**。経験5万件で約1.7GB、実働で**約4GB**。10万件なら3.4GB、20万件なら6.8GBと線形に増える | 推奨構成16GBで実働の4倍の余裕 |
| NFR-07 | プリセット生成は現実的な時間で終わる | **目標** | 実測 **約35分**（5,000ステップ） |

> **区分の読み方**: 「目標」は守りたい要求、「設計決定」はそれを満たすための手段、
> 「制約」は変えられない前提、「方針」は数値目標を置かない意思決定です。

### 3.2 コスト

| ID | 要件 | 区分 | 現状 |
|---|---|---|---|
| NFR-08 | 個人開発として継続可能な月額に収める | **目標だが上限値は未設定**（§8 参照） | 試算 **約 ¥8,900/月**（年 ¥107,000） |
| NFR-09 | 計算資源は安価な調達方式を使う | **設計決定** | 全インスタンスを Spot（AWS の余剰枠を最大7割引で借りる。ただし2分前通知で強制停止されることがある）で調達 |
| NFR-10 | 稼働していない時間は課金を止める | **目標** | 定時 start/stop で実現。ただし固定費が残る（下記） |

> **現状の最大費用項目は VPC エンドポイント（インターネットを経由せず AWS 内部で他サービスに
> 繋ぐ出入口）の月 ¥3,300 で、全体の約 37%**。サーバを止めている間も24時間課金されるため、
> NFR-10 を完全には満たせていません。削減案（公開サブネットへ移す等）は保留中です。

### 3.3 可用性・耐障害性

| ID | 要件 | 区分 | 現状 |
|---|---|---|---|
| NFR-11 | 強制停止で**学習成果を失わない** | **目標**（必須） | 実装済。停止シグナル→保存→S3退避の経路を整備し、静的検査12件で固定 |
| NFR-12 | 停止・起動をまたいで状態が残る | **目標** | 実装済（サーバ停止でもディスクは保持されるため） |
| NFR-13 | 障害からの復帰 | **方針: 手動で可**とする | 自動再起動は意図的に持たない（§4 参照） |
| NFR-14 | 配信が一時的に落ちても、視聴側は自動で復帰する | **目標** | 実装済（クライアントが2秒ごとに再接続） |

### 3.4 運用性・保守性

| ID | 要件 | 区分 | 現状 |
|---|---|---|---|
| NFR-15 | 日々の運用に人手を要しない | **目標** | 定時起動・祝日スキップまで自動。Spot 中断時のみ手動 |
| NFR-16 | 設定値は設定ファイルに集約し、コードに埋め込まない | **方針** | YAML 4ファイル（world / physics / reward / training） |
| NFR-17 | 設計変更の経緯を追跡できる | **方針** | `design_change_record.md` に旧仕様の読み替え表を維持 |
| NFR-18 | 暗号化通信で配信する | **目標** | 実装済（Caddy による自動 TLS） |

## 4. スコープ外（意図的にやらないこと）

**「できていない」のではなく「やらないと決めた」もの**です。要件定義書で最も省略されがちで、
しかし最も効く節だと思います。判断理由も併記します。

### 4.1 プロダクトとして持たない機能

| やらないこと | 理由 |
|---|---|
| 視聴者の操作・介入 | 一方向のアンビエント配信に絞る |
| アカウント・認証 | 誰でも見られることを優先 |
| カメラ操作 | 固定カメラのみ。構図を作り込む方を選ぶ |
| スコア・ステージ表示などの UI | 接続状態の表示のみ。メタ情報は見せない（FR-09） |
| ロボットハンドの描画 | 掴む腕は見せない。積み木だけが動く |
| 音声・BGM | 検討していない |
| **上手すぎる AI** | コンセプトに反する。意図的に壁の手前で止める（FR-25） |

### 4.2 技術的に採用しなかった選択肢

| 不採用 | 理由 |
|---|---|
| ロードバランサ（ALB / API Gateway） | 視聴15人規模で過剰。EIP + Caddy で足りる |
| ElastiCache Redis | 共有状態を持つ必要がなかった（復活条件は `aws_deployment.md` 付録D） |
| NAT Gateway | VPC エンドポイントの方が安い（月 $35 → $22） |
| GPU インスタンス | ニューラルネットが小規模で、物理計算が CPU 律速。GPU が活かせず月¥3,600→¥480に削減 |
| **Auto Scaling Group** | 最小0・最大1で運用していて一度もスケールしなかった。実態はオン/オフスイッチ |
| **ECS Fargate** | 物理コアを専有できず NFR-03 が成立しない。永続ディスクも無い（詳細は `design_change_record.md`） |
| ステージの降格 | 一方向に進むのみ |
| **AI の進級判定** | 自動判定が誤検出して事故を起こしたため撤去。固定ステップ制に置き換えた（§9 参照） |
| 学習の中断・再開 | 毎回ゼロから。再開が必要な連続学習は `live_server` 側が担う |
| 定期チェックポイント保存 | 1回の学習で保存は1本だけ |

### 4.3 将来やるかもしれないこと（今回は範囲外）

優先度付きの一覧が `aws_deployment.md` 付録F にあります。最有力は
**長期記憶の永続化**と**停止期間中の重み減衰（寝ている間に少し忘れる挙動）**のセット実装。
コストが小さく、子供メタファーとの相性が良いという評価です。

逆に**やらない方が安全**と結論が出ているものもあります（観測値にノイズを乗せる案）。

## 5. 受入条件（どうなったら「できた」と言えるか）

> **注意: この節は本資料で新しく提案するものです。** 元の設計書に完成の定義は存在せず、
> 以下は既存の要件から逆算した案です。合意された基準ではありません。

### 5.1 最低限これが成立したら「動いている」

- [ ] クライアントを起動すると接続でき、積み木が動いて見える
- [ ] AI が掴む→運ぶ→置くを繰り返し、ときどき塔が崩れる
- [ ] 画面が目に見えてカクつかない（NFR-01 / NFR-03）
- [ ] 1日稼働させた翌日、前日の続きから再開している（FR-22）
- [ ] 強制停止させても、その日の学習成果が残っている（NFR-11）

### 5.2 「サービスとして成立した」と言うための条件

- [ ] 1ヶ月連続運用して、手作業の介入が Spot 中断対応だけで済む（NFR-15）
- [ ] 月額が想定内に収まる（NFR-08。ただし上限値が未設定なので先に決める必要あり）
- [ ] 月初のプリセットから月末まで、**成功率が目に見えて上がっている**
      — これが「成長を配信する」の実質的な達成条件
- [ ] 視聴者が複数同時接続しても配信が破綻しない（NFR-04。実測未確認）

### 5.3 まだ測る手段が無いもの

「アンビエント配信として面白いか」は現状**測定方法がありません**。視聴維持時間や
再訪率のような指標を取る仕組みは実装されていません。個人開発の演習としては
後回しで構いませんが、「何をもって成功とするか」が未定義であることは認識しておくべき点です。

## 6. 制約条件

| 区分 | 制約 |
|---|---|
| 体制 | 個人開発。レビュー者がいないため、設計判断の記録を残すことで代替している |
| 開発環境 | Python は `.venv` 内の python.org 製 CPython 3.12 を直接使う。`uv sync` は使えない（物理エンジンのビルド互換の問題） |
| 物理エンジン | PyBullet は**単一スレッド**。並列化で1ステップは速くならない（NFR-01 の制約そのもの） |
| 記憶容量 | 長期記憶の件数とメモリ使用量が線形。インスタンスの RAM が上限を決める（NFR-06） |
| 並列数 | 学習の並列数は保存データの形に焼き込まれるため、**途中で変更できない**（変えると長期記憶を捨てることになる） |
| クラウド | 東京リージョン。全て Spot なので強制停止を前提に設計する |
| クライアント | Godot 4.4.1 .NET 版。C# ビルドに .NET 8 SDK が必要 |

| **稼働時間の要求が矛盾している** | コンセプトは「**24時間稼働**」、運用計画は「**平日 10-18時**（月176時間）」 | §9 参照。**本資料を書いて見つかった最大の乖離**。どちらが要求なのか決まっていない |

| 稼働スケジュールの具体値 | プリセット生成: 月初1日 09:00（5,000ステップ）/ 配信: 平日 10-18時 | 時間帯・頻度・ステップ数のいずれも実績ゼロ |
| プリセット生成用サーバ | 16 vCPU のインスタンス | 1コアで35分回すだけなので明らかに過剰。小型化するか配信サーバの月初処理に畳み込む案がある |
| 配信サーバの構成段階 | 推奨構成（3段階を提示済み） | 実配信でのコマ落ち具合を見て確定させる |
| 同時視聴15人の実測 | 未検証 | 実際に複数接続した計測をしていない |
| 積み木配置の永続化 | 保存先だけ用意済み | 読み書きの実装が無い。崩れた配置を翌日に引き継ぐかどうかも未決 |
| Spot 中断からの復帰 | 手動で起動 | 自動再起動を意図的に手放した。中断頻度を見てから自動化を判断 |
| 成功の測り方 | 未定義 | §5.3 参照 |

## 9. 後付けで書いて分かったこと

勉強会で話したい本題はここです。**要件定義書を書かずに設計から進めると何が起きるか**の
実例になりました。

### 9.1 要求と計画が矛盾していても、誰も気づかない

設計書の冒頭には「**24時間稼働**のアンビエント配信」と書いてあります。
一方 AWS の運用設計は「**平日 10-18時**、月176時間」です。**4倍以上違います。**

どちらも正しく書かれていて、どちらも嘘ではありません。ただ**並べて書かれていなかった**ので、
矛盾として認識されませんでした。要件を1箇所に集めると、こういうものが落ちてきます。

> **学びポイント: 要求を1枚に集める価値は、新情報より「矛盾の発見」にある**
>
> 設計書は分量が増えるほど、離れた場所の記述同士が食い違っても気づけなくなります。
> 要件定義書は新しいことを書く場所ではなく、**散らばった要求を突き合わせる場所**として
> 効きました。

### 9.2 「目標値」と「実測値」が区別されていなかった

元の設計書には数値が大量にありますが、**それが守るべき目標なのか現状の測定結果なのかが
書かれていません**。例えば「2.5ステップ/秒」は実測値で、別に速くしたいわけではありません
（むしろ遅くていい）。一方「240Hz」は守らないと破綻する目標です。

この区別がないと、改善の余地があるのかないのかが判断できません。§3 で区分を付け直したのが
本資料の実質的な成果です。

> **学びポイント: 数値には「目標 / 設計決定 / 制約 / 実測」のラベルを付ける**
>
> 同じ「240」と「2.5」という数字が、全く違う意味を持っています。ラベルがないと、
> 後から読んだ人（半年後の自分を含む）が取り違えます。

### 9.3 完成の定義が無いと、暫定値が永遠に暫定のままになる

AWS の稼働スケジュールが「暫定」のまま確定しないのは、意思決定が遅れているからではなく、
**何をもって確定とするかの基準が無い**からでした。「1ヶ月運用して介入がN回以下なら確定」
のような受入条件があれば、判断できます。

§5 で受入条件を提案しましたが、これは**元の設計書に存在しなかった**ものです。

> **学びポイント: 「暫定」が長く残っているのは、判断基準が無いサイン**
>
> 決断力の問題に見えて、実は受入条件の不在であることが多い。

### 9.4 一方で、設計を先に書いたことは無駄ではなかった

誤解のないように書いておくと、**このプロジェクトは設計から入って成功している部分も大きい**です。

- 「なぜその技術を選んだか」の記録（`tech_stack.md`、付録E）は、要件定義書より
  実務では引く回数が多い
- 3層記憶のようにコンセプトを技術に落とす部分は、**手を動かさないと設計できなかった**
- 採用しなかった選択肢の記録が残っているので、同じ検討を繰り返していない

要件定義書が無かったことで損をしたのは、§9.1〜9.3 の3点に集中しています。
**全部を前工程で書く必要はなく、「要求・目標値・完成条件」だけは1枚にまとめる価値がある**
というのが、今回の結論です。

## 付録. 用語

| 用語 | 意味 |
|---|---|
| 強化学習 | 試行錯誤と報酬から行動方針を学ぶ機械学習の一分野 |
| SAC | 本プロジェクトで使う強化学習アルゴリズム（Soft Actor-Critic） |
| ステップ | AI の1手。学習の進み具合は累計ステップ数で測る |
| エピソード | 1プレイ分。積み木を何手か置いて崩れるか時間切れになるまで |
| 報酬 | 1手ごとに AI へ渡す点数。何を教えたいかの設計そのもの |
| replay buffer | 過去の経験を貯めておく箱。SAC はここから引き直して学習する |
| カリキュラム学習 | 簡単な課題から順に難しくしていく学習方法 |
| プリセット | 配信の種になる学習済みモデル。月次で生成する |
| Spot インスタンス | AWS の余剰枠を安く借りる方式。最大7割引だが強制停止される |
| VPC エンドポイント | インターネットを経由せず AWS 内部で他サービスに繋ぐ出入口 |
| Caddy | 自動で TLS 証明書を取得・更新する Web サーバ |
